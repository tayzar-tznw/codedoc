# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This repository is **codedoc_go_leiden**, the fork of `codedoc_go` that changes one thing: **topics come from Leiden community detection** on the resolved code graph instead of the LLM's discovery. Phase 4a (in `--graph`, no LLM) decides the membership; Gemini only names the topics (Phase 4b) and writes their pages from structural evidence (Phase 5). `python -m graph_generator compare-topics` compares both ways on the same repo and commit. Everything else (gohelper, discovery, resolution, gates, the other tables, evaluate, trial) is codedoc_go's.

CodeDoc ingests **plain Go modules** (`go.mod`, `go.work`, module and workspace `vendor/`, local `replace`), loads a code knowledge graph into Cloud Spanner for Graph-RAG querying, and writes Japanese wiki pages and per-declaration summaries with Gemini. Only `.go` files are scanned, by the go command's own skip rules; the tool itself is Python 3.12+ on GCP (Vertex AI Gemini + Spanner). Extraction and resolution are done by **gohelper**, a Go program in `gohelper/`: `gohelper extract` uses go/parser (stdlib only) and `gohelper resolve` runs one `golang.org/x/tools/go/packages` + `go/types` load per group and build configuration (x/tools v0.52.0 vendored). There is no language server and no tree-sitter. The pinned toolchain is **go1.27.2** (`setup go`); gohelper needs go ≥ 1.26.0 (`gohelper/go.mod`). A resolver answer only becomes an edge when it is certain. GOPATH mode, Bazel, cgo resolution and framework conventions (wire, fx, reflection routing, `go:generate`) are out of scope.

All user-facing docs (README.md, docs/ARCHITECTURE.md, docs/LSP_RESOLUTION.md, docs/GRAPH_SCHEMA.md, docs/CROSS_PROJECT.md, sample_prompt.txt) are in **Japanese — keep edits and examples Japanese**, MECE (one owner per fact, link instead of repeating), short sentences, tables for reference facts, no marketing words, no emoji, measured numbers only with a date. `docs/LSP_RESOLUTION.md` keeps the family's file name although Phase 1.6 uses go/types, not a language server. The canonical doc example is F1's `FeeCalculator.Calculate` in module `example.com/iryo/billing`. This file and `mcp_server/README.md` are English, as are the design spec and plans under `docs/superpowers/` (this variant's spec: `docs/superpowers/specs/2026-10-13-codedoc-go-leiden-design.md`). `docs/ARCHITECTURE.md` keeps the dated topic comparison results.

**Fork convention.** `scripts/sync_from_codedoc_go.sh` copies `../codedoc_go` over this tree except the leiden-owned paths in `scripts/leiden_owned.txt` (the topic modules and tests, `docs/superpowers/`, and the adapted README.md, CLAUDE.md, sample_prompt.txt, docs/ARCHITECTURE.md, docs/GRAPH_SCHEMA.md, mcp_server/README.md) and local state (`.env`, `.venv`, `.adk/` at any depth, output dirs, `webapp/frontend/node_modules` and `dist`), then `scripts/leiden_hooks.py apply` and `verify` re-apply the `LEIDEN-HOOK` edits to the shared files. Change shared code in codedoc_go and sync; in this tree, change a shared file only through a hook (an anchor that moved stops the sync with the hook's name). `docs/LSP_RESOLUTION.md` and `docs/CROSS_PROJECT.md` are codedoc_go's, synced as they are; port codedoc_go's later edits of the adapted docs with `git merge-file` against the codedoc_go version they were adapted from.

## Environment & commands

The venv is **uv-managed (Python 3.13, no pip binary)** — use `uv pip … --python .venv/bin/python`:

```bash
uv venv --python 3.13 .venv
uv pip install --python .venv/bin/python -r requirements.txt   # requirements.txt is a full freeze; pin new deps
cp .env.example .env    # or: python -m graph_generator init   (interactive)
python -m graph_generator setup go   # installs go1.27.2 (SHA-256 pinned, linux/amd64) into .tools/go, if you have no go
```

Phase 4a needs `graspologic-native==1.3.1` (with numpy and scipy) and `networkx==3.7`, pinned in `requirements.txt`. A backend that cannot be imported is a preflight error in every mode, doctor included (exit 3); there is never a fallback to another algorithm. Topic settings: `TOPIC_MIN`/`TOPIC_MAX` (level-1 count band, 5/25), `SUBTOPIC_MIN_ATOMS` (12), `TOPIC_PROFILE` (`strict`, or a `+` combination of `degree_norm`, `calls_only`, `no_implements`, `with_tests`), `TOPIC_SEEDS` (`42,43,44,45,46`).

There is exactly **one `.env`, at the repository root**. The pipeline, `graph_query_agent/config.py`, `webapp/main.py`, `mcp_server/runner.py` and `mcp_server/deploy.sh` all read it. Never create `graph_query_agent/.env`: `adk run` loads the first `.env` found walking up from the agent directory, so a nested file would shadow the root one.

The toolchain is `GO_TOOLCHAIN`, else `.tools/go/bin/go`, else `go` on `PATH`. Every go command and gohelper run gets an environment built from scratch by `go_toolchain.env_for` (`GOTOOLCHAIN=local`, `GOENV=off`, `GOFLAGS=-mod=readonly|vendor -modcacherw -buildvcs=false`, caches under `OUTPUT_DIR/go/`); `-modfile` and build tags go on the command line, never in `GOFLAGS`. When you run go by hand against a repo, keep `GOTOOLCHAIN=local` and `-buildvcs=false`.

Pipeline CLI (`graph_generator/__main__.py`; exit codes 0 ok, 1 other errors, 2 usage, 3 preflight failure, 4 `--wiki` precondition failure):

```bash
python -m graph_generator doctor [<dir>]                       # preflight table: builds, toolchain, gohelper build, memory, groups, offline modules, Spanner, Gemini, Leiden backend, topic settings

python -m graph_generator validate                             # row counts + orphan-edge checks (tables from NODE_SPEC/EDGE_SPEC)
python -m graph_generator crossref [--dry-run]                 # cross-repo edges, after all repos are ingested
python -m graph_generator evaluate [--fixture NAME] [--env]    # GCP-free, network-free regression gate on test_codes/ (needs a Go toolchain)
```

## Architecture

**Pipeline (`graph_generator/pipeline.py`, graph first, Phase 7 is absent):**
- Graph track (`run_graph_track`): Phase 1 scans with the go command's skip rules, records each file's SHA-256 and discovers modules and groups from files only, with the build configurations from `GO_BUILD_*`/`GO_EXTRA_BUILDS` (`go_units.py`; writes `units.json`) → Phase 1.5 `gohelper extract` (`go_extract.py`, `entities.json` v1) → Phase 1.6 `gohelper resolve` per group × build, classification and gates (`resolution.py`, `resolutions.json` v1) → Phase 4a communities (`topics_phase.phase4a_communities`, on the builder rows, before Phase 8) → Phases 8–9 node and edge rows (`graph_rows.py`), always written to `graph_rows/<Table>.jsonl` and, unless `--no-spanner`, upserted to Spanner → the five topic tables (`topics_phase.write_graph_topics`). Re-ingest deletes the rows the previous run wrote to the same target and this run did not: Phase 8 records their keys in `graph_prune.json` before it rewrites `graph_rows/`, and the deletes follow the Phase 9 upserts. Phase 8 also re-applies cached wiki summaries to Spanner (no LLM call). The finished state goes to `pipeline_data.pkl`.
- Wiki track (`run_wiki_track`, only after `prepare_wiki` accepts the repo): Phase 1 re-scan → Phase 2 node summaries (`node_summaries.py`: one batched call per file with graph context read from `graph_rows/*.jsonl`; per-node calls above `WIKI_FILE_MAX_CHARS` / `WIKI_FILE_MAX_NODES`; closures, `<init>` and, unless `WIKI_SUMMARIZE_GENERATED=1`, generated files get no call) → Phase 3 package and directory summaries → Phase 4b topic names → Phase 5 topic pages → Phase 6 index → Phase 10 write-back (summary columns; the five topic tables deleted and re-inserted per repo and `ID_PREFIX`, in commits of 2,000 rows, not atomic; embeddings for Files, Packages, Classes, Methods without closures and `<init>`, and Topics). Prompts are Japanese, in `prompts.py`; bump `PROMPT_VERSION` whenever a prompt changes, because it is part of every summary cache key.
- **Freshness:** positions from an old extraction are never paired with fresh resolution answers. Entities are reused only when every scanned file's sha256 and stamp match (stamp = `EXTRACTOR_REVISION`, the gohelper source hash, the primary build configuration, the owning go.mod and module path); otherwise one gohelper call re-extracts every file, because receiver owners and build twins read sibling files. Bump `go_extract.EXTRACTOR_REVISION` when the stored records change for the same helper output. Phase 1.6 re-hashes every file first (`refresh_entities`, `StaleEntitiesError` when a file that had entities loses them), refuses entities that differ from disk before the first load (re-extracted once), and marks sites in, or pointing into, a file whose loaded or current bytes differ from its entities `unresolved` (`stale`). `resolutions.json` is rebuilt every run and written atomically. `graph_checkpoint.json` stores `id_scheme`, `file_hashes`, the hash of `resolutions.json` without `stats`, the communities hash (`topics_phase.document_hash`: communities.json without its carry-over bookkeeping) and the Spanner target; any change rewrites nodes and edges from Phase 8. `--wiki` refuses (exit 4) unless the checkpoint is complete with the same ID scheme, the re-scan's hashes equal the checkpoint's, the Spanner target matches, the last `--graph` produced communities, `topics/communities.json` matches the checkpoint and `graph_rows/` still give its projection.
- **Caches:** Phase 2 records `summaries/nodes/<relpath>.json` keyed by (file sha256, graph-context hash, `PROMPT_VERSION`, model), in `WIKI_SUMMARY_CACHE/<repo>` (shareable with codedoc_go) and always in the per-repo `summaries/`; package and directory summaries are keyed by their children's summaries; Phase 4b keeps the name of a topic whose ID is unchanged or that matches, at Jaccard ≥ 0.6, a topic the last 4b named (`topics/names.json`, `topics/named_communities.json`; any number of --graph runs may come between), and Phase 5 reuses a page while its prompt and the model are unchanged (`topics/pages.json`), so a changed membership always gets a new page; embedding vectors are cached in `embeddings/cache.sqlite` by (sha256 of the text, `EMBED_MODEL`, `EMBED_DIMENSION`); the gohelper binary is cached as `OUTPUT_DIR/go/bin/gohelper-<go version>-<source hash>`.
- Everything is configured through the root `.env` → `graph_generator/config.py` (`GO_*`, `WIKI_*`, `PEER_REPOS`, Spanner names; `GRAPH_NAME`/`ID_PREFIX` allow side-by-side graphs in one DB). `GOOGLE_CLOUD_PROJECT` has no hardcoded default anywhere: when it is unset, the Google client libraries use the ADC / gcloud default project, and the commands and the agent print the project they use.

**Topics (`graph_generator/topics/`, pure: rows in, rows out, no GCP; glued in by `topics_phase.py`):** atoms are `Classes` rows (types plus each file's `<package>` pseudo-type); a method belongs to its `class_id`, a closure to its outermost declaration's owner. Profile `strict` clusters only production atoms (origin package or command, not generated, built by the primary build) over exact facts: `MethodCalls` (`types` or `convention:*`; interface methods as `iface_call`), `ClassEmbeds`, `ClassImplements`, weighted `Σ α·min(log2(1 + n), cap)` over distinct (caller, callee) method pairs; never `PossiblyCalls`, external targets, directories or names. Leiden runs one `graspologic_native.leiden` call per seed and resolution on a canonical input (no isolates, no zero or NaN weights, no `starting_communities`), picks the best trial by modularity at its resolution (ties: smallest membership hash) and the largest resolution on the longest count plateau inside `[TOPIC_MIN, TOPIC_MAX]`, then splits level-1 topics above `SUBTOPIC_MIN_ATOMS` primary atoms at γ 1.0 when at least two children keep 3 atoms. Thin groups merge into their strongest neighbour; other atoms are attached (roles `attached-file`, `attached-test`, `attached-generated`, `attached-excluded`) or go to the one unassigned topic per repo (role `unassigned`, `label_source = fixed`, never sent to the LLM). `topic_id = _make_id("topic", repo, "L<level>", membership_hash)` over the primary members, so names never change IDs; names (not pages) carry over at Jaccard ≥ 0.6. `community.check_integrity` (each level covers every atom once, children partition their parent, IDs match) and any backend failure stop Phase 4a only: the graph is written without topics and `--wiki` refuses. The same input gives the same `communities.json` apart from carry-over bookkeeping. Phase 5 pages come from a bounded evidence package with Mermaid scaffolds of real edges (an added edge restores the scaffold) and end with a grounding check of backticked identifiers against the graph's names.

**Discovery never runs anything against the repo (`go_units.py`, `go_modcache.py`, `go_toolchain.py`):** go.mod, go.work, `vendor/modules.txt` and build constraints are parsed in Python (ports of x/mod modfile, modload and go/build from go 1.27.2), and discovery reads only a Go file's header (build constraints, package clause, imports). A module's group is the go.work found walking up from its root if that go.work lists it, else a single-module group (`GOWORK=off`); each module is in exactly one group. Each group gets a control directory `OUTPUT_DIR/repos/<repo>/go/<group>/`, recreated every run: a generated go.work with absolute paths (workspace) or a go.mod/go.sum copy passed with `-modfile` (single module), plus peer `replace` lines; the go command writes `go.work.sum`/go.sum there, never into the repo, and `-buildvcs=false` keeps `.git/index` untouched. Offline (default), modules come from a consistent `vendor/`, else from the user's module cache read as a `file://` proxy into the isolated `OUTPUT_DIR/go/modcache` (the user cache is never written), else nowhere (`unresolved`, `missing-module`). `--download-modules` fetches only what `go list -deps -test` needs, from the user cache first, then `GO_PROXY`, checked against go.sum and `GO_SUMDB`; single-module groups download with `-mod=mod` on their control go.mod copy, which is then put back byte for byte (only the go.sum fill stays), so the readonly load sees the developer's module graph: an import the repo's go.mod does not require fails as in the developer's build, and a warning (`go.mod lacks requirements for: …`) names the missing requirements and their importing packages. A `go` line of the group's go.mod or go.work newer than the toolchain fails the group closed (status `toolchain`); a newer `toolchain` line or dependency `go` line only warns. A group whose load fails gets status `error`, its sites become `unresolved` (`toolchain` or `load-error`), and other groups continue. `go_units.stops` names the discovery problems that stop a run (every group too new: exit 3); other discovery findings only warn.

**gohelper (`gohelper/`, protocol 1):** `gohelper version | extract | resolve`; JSON Lines on stdout (resolve also `--out FILE`), diagnostics on stderr, exit 0 unless the invocation is invalid (2) or the output cannot be written (1) — load errors are records. `go_toolchain.ensure_helper` builds it during preflight with `go build -mod=vendor -trimpath -buildvcs=false` and refuses a toolchain older than the `go` line of `gohelper/go.mod`. Positions are unadjusted (`PositionFor(p, false)`, so `//line` never moves them): lines 1-based, columns 1-based bytes, offsets 0-based bytes, no UTF-16 anywhere. Extract and resolve join on (relpath, byte offset of the callee token); if you change what either side emits, update `go_extract.py`/`resolution.py` with it and re-record `tests/fixtures/helper/`.

**Resolution per site (`resolution.py` → `go_classify.py` → `go_gates.py`):** the helper classifies the callee (builtin, conversion, func, method, iface, typeparam, value, funclit, linkname, unknown); Python classifies the target's real path (GOROOT builtin or stdlib, peer module dir, module cache, vendor, scanned file, unscanned file, cgo, outside the repo) and maps an in-repo target to a node only at the exact name range of a node of the expected kind (`DeclIndex`; no enclosing fallback). Rules `funclit`, `func-alias` (a local variable bound once, proven from go/types), `linkname` and `range` record `via = convention:<rule>`; gates G1–G10 refuse what is not certain. G3 (`embed_invalid`) also refuses a promoted selection when a package declaring a type on its embedding path, the receiver's included, may have lost a declaration (syntax errors, a file the type checker ignored for its package clause, a dropped embedded field: R43, `gohelper/internal/resolve/broken.go`). Implementers are checked method by method, because go/types reports a type with an embedded field of invalid type as implementing every interface: a winning method of another signature means no implementer (R52). Implements records the helper marks `incomplete` stay unresolved, and a record whose candidates lack an out-of-repo candidate reached through an embedded interface carries `candidates_partial: "via_embedded_external"` (its PossiblyCalls rows are unchanged). Interface calls are open-world: a `MethodCalls` edge to the interface method plus `PossiblyCalls` (reason `implementation`, column `open_world`) to the in-repo implementers, never a single-implementer upgrade. Conversions are dropped and counted. There are no name-heuristic candidates.

**Edge derivation invariant (Phase 9, pure `derive_edge_rows` in `graph_rows.py`):** `MethodCalls` come **only** from `resolved` records whose target is a `Methods` node of this repo; `PackageImports`, `ClassEmbeds` and `ClassImplements` only from `resolved` records whose ends are nodes of this repo. `external`, `builtin`, `dynamic` and `unresolved` are counted, never edged; peer targets are left to `crossref`. `PossiblyCalls` go to the in-graph candidates of `resolved`, `external` and `ambiguous` records, and above `POSSIBLY_CALLS_MAX_CANDIDATES` a site writes no rows. **Zero wrong edges** is the hard guarantee, measured by `evaluate`. Pure builders `build_node_rows`/`derive_edge_rows` do all derivation without GCP, and their rows carry exactly `write_columns(table)`. If you change what the extractor or resolver emits, check `go_classify.DeclIndex` and `derive_edge_rows` together.

**Node identity (`_make_id(kind, repo, relpath, qualname)`, `ID_SCHEME = 1`):** an ID is `<ID_PREFIX>_` + the first 16 hex chars of SHA-256 over the NUL-joined inputs. Packages use (directory, package clause); classes and methods use the declaration's relpath and qualname (`T.M`, `I.M`, closures `F.func1`, `init#k`, `<init>` for package-variable initializers, the per-file `<package>` pseudo-type, blank functions and methods `_#k` / `T._#k`). The module path is a **column**, never an ID input. Repos are islands in one graph; only `crossref` writes `CrossRepoCalls`/`CrossRepoRef`/`CrossRepoImports`, from peer targets recorded in `resolutions.json` (no name guessing; drops, including `stale` files whose resolutions hash differs from the entities hash, go to `OUTPUT_DIR/crossref_report.json`). It prunes its own previous edges to the same target the same way (`OUTPUT_DIR/crossref_rows.json`). Bump `ID_SCHEME` whenever `_make_id` inputs change.

**Graph & query stack:** `graph_generator/setup_spanner_graph.py` (`NODE_SPEC`/`EDGE_SPEC`, the single source of truth for DDL, the property graph, insert column lists, migrations and `validate`) creates 6 node tables and 17 edge tables: codedoc_go's 14 plus `ClassBelongsToTopic`, `TopicDependsOn` and `TopicContainsTopic`, which `topics_schema.extend` adds together with the extra `Topics` columns and `FileBelongsToTopic.role` (a hook in `setup_spanner_graph.py`); preflight stops when the database's tables, columns or column types drift from them (`setup_spanner_graph.schema_drift`). `Classes` holds Go types (struct, interface, named, alias, plus the `<package>` pseudo-type); `Topics` are structural Leiden topics, not Go modules (the `module` columns hold module paths). `graph_query_agent/agent.py` carries both topic layers and selects this one with `TOPIC_SOURCE = "leiden"` (a hook). `graph_query_agent` is a two-ADK-agent setup — `root_agent` delegates to `graph_agent`, which holds the read-only `run_gql_query` (snapshot reads, at most 50 rows, values cut at 500 characters); settings come from `graph_query_agent/config.py`. The graph agent's instruction is passed as an InstructionProvider function, not a string: ADK substitutes `{name}` placeholders in string instructions from session state, and the GQL braces and qualnames such as `<init>.func1` would break. `scripts/gql_lint.py` checks every cookbook query in the instruction, the skill (`.claude/skills/codedoc-query/SKILL.md`) and the docs against `NODE_SPEC`/`EDGE_SPEC`. `mcp_server/` (FastMCP over HTTP) and `webapp/main.py` (FastAPI) wrap the agent; the webapp serves `OUTPUT_DIR/repos/<repo>/` chosen by `?repo=`, else `WEBAPP_REPO`, else the only repo.

**Deploy defaults:** `mcp_server/deploy.sh` reads the root `.env` (`GOOGLE_CLOUD_PROJECT`, `SPANNER_INSTANCE`, `SPANNER_DATABASE`, `GRAPH_NAME`, `GOOGLE_CLOUD_LOCATION`, `GEMINI_MODEL`) and defaults to Spanner `codedoc-instance` / `codedoc-go-leiden`, Cloud Run service `codedoc-go-leiden-mcp`, image `codedoc-go-leiden-mcp` in Artifact Registry repo `codedoc`, runtime service account `codedoc-mcp-sa` (shared with the sibling variants). The service and database names differ from the siblings' on purpose (codedoc_go uses `codedoc-go` and `codedoc-go-mcp`), so deploying this variant never replaces theirs. `tests/test_deploy_script.py` runs the script against a fake `gcloud`. No Dockerfile bakes in a `.env`; settings come from the container's env vars.

## Test fixtures (`test_codes/`)

Three committed fixtures, all pinned to **go1.27.2, `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`, no tags, `go 1.26` lines**. They are the eval target for `python -m graph_generator evaluate`. Third-party modules come only from the committed synthetic proxy `test_codes/_proxy` (`build_proxy.py`; `--check` verifies the committed files are reproducible).

- **F1 `iryo-kanri-system/`** — the Go port of the C#/Java/Python hospital-management corpus: 13 modules under `example.com/iryo/...` and `example.com/thirdparty/textfmt`, 12 of them in the root `go.work`. `admin-console` is outside it (single-module group, `GOWORK=off`, local `replace`s, the published textfmt v1.1.0), while the workspace builds the in-repo fork `third_party/textfmt` (same module path). Apps `reception-desk`, `admin-console`, `patient-portal` (`net/http` with `httptest`). Keeps the XPR pairs (byte-identical procedure code whose imports differ) and the name twins across modules. Also holds `ground_truth/qa_questions.json` (QA gate) and `features.json` (the reviewed features of `compare-topics --features`, written from the corpus design before any topic run).
- **F2 `go_layouts/`** — 23 small layout repos for discovery: nested modules, workspaces, workspace and module vendor, local replaces inside and outside the repo, a missing `use`, too-new `go` and `toolchain` lines, a dependency with a newer `go` line, missing go.sum lines, files under no go.mod, skip dirs, go.mod `ignore`, `//go:build ignore`, symlinks, cgo twins, `//line` directives, dot imports, a non-ancestor go.work, two go.work files, inconsistent vendoring. `ground_truth/expected_units.json` pins the discovery facts.
- **F3 `multi_repo/`** — repos `shared`, `web`, `api`, ingested as peers of each other, with an exact cross-repo edge set (`ground_truth/expected_cross_repo_edges.json`) and negative controls (a fork provided by two peers, a vendored peer copy, an undeclared peer dependency, a peer path the module already replaces).

Ground truth per fixture lives only in `ground_truth/`: `cases.py` (snippet-keyed source of record, no line numbers; F1 adds `DECL_PINS`) → `test_codes/_gt/generate_manifest.py` → `manifest.json` → `test_codes/_gt/check_ground_truth.py` (standalone, stdlib only, must exit 0) and `test_codes/_gt/run_oracle.py` (builds the runtime oracle goracle from `test_codes/_gt/oracle`, instruments a copy of the fixture, runs every entry of `entries.json` and judges each executed case; needs go1.27). Run each as `python3 test_codes/_gt/<tool>.py test_codes/<fixture>` from the repository root. The tools have their own suite: `cd test_codes/_gt && ../../.venv/bin/python -m pytest`. `expect` follows Go's semantics under go1.27.2 and the spec's rules, and is **never generated from resolver output**.

`test_codes/` is synced from codedoc_go: make fixture changes there, then sync. Rules when touching fixtures:
- After ANY fixture edit, run generate_manifest → check_ground_truth → run_oracle for that fixture, then `evaluate` in both modes. If `generate_manifest.py` names a case whose snippet became missing or non-unique, fix the snippet in `cases.py`, not the tooling.
- The name collisions and byte-identical pairs ARE the test — never dedupe or rename them, and never add comments to fixture code (only the comments Go gives meaning to: `//go:build`, `//go:linkname`, the `// Code generated ... DO NOT EDIT.` header). Intent lives in the READMEs and the `why` fields.
- A new type that satisfies an interface changes that interface's cases (`candidates`, `open_world`); types in test files count.
- Keep fixtures and the ground-truth tools standalone — no imports from or assumptions about `graph_generator` internals.
- Fixture `go.sum` files and `vendor/` directories are generated from `_proxy` (`_proxy/sums.txt` holds every go.sum line); never edit them by hand. The F2 and F3 READMEs say how to regenerate them.
